# Rules

1. Never commit or push unless explicitly requested by the user.
2. Always use conventional commits style (e.g. `feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, etc.).
3. This is a SolidJS repository, not a React repository. You may not do inline maps or inline IIFEs in JSX, as those break Solid's ability to track elements. Use `<For>` instead of `.map()` and `<Show>` instead of conditional IIFEs.
4. Every commit that introduces a user-facing change must add an entry to `src/lib/changelog.ts` before committing, at the top of today's day group, creating today's `{ date: "YYYY-MM-DD", changes: [...] }` group if it does not exist yet. Days run newest first and entries within a day run newest first, and `kind` is one of `New`, `Improved`, `Fixed`, or `Removed`. That file is the project's only changelog and it powers the in-app `/changelog` page; do not add a standalone `CHANGELOG.md`. Write entries for people using the app, not developers: say what they can now do, see, or experience. For fixes you may explain why at a more technical level when it helps the reader. Keep entries concise. Use existing entries in the file as examples.

# API quirks

If a new API quirk has been discovered, please document it here in #API Quirks section.

- Login response is **snake_case** (`blog_id`, `blog_name`, `user_id`).
- `resolveIdentifier` returns **camelCase** (`blogId`, `blogName`).
- `listBlogActivity` request fields are **snake_case**; pagination always uses `page: { page_size, page_token? }` (cursor-based, never `page` as an integer) and `page_size` is duplicated at the top level of the request; the search query is `q`.
- `listBlogActivity` `activity_kinds` **must include `"like"` or `"comment"`**. A request with only `['post', 'reblog']` makes the server switch to offset-based pagination — the token contains `result_offset` and the server echoes the same page/token forever (infinite loop). Including `like`/`comment` (e.g. `['post', 'reblog', 'like', 'comment']`) switches it to a dual-cursor token (`activity` + `posts`) that advances correctly. When both activity kinds are present, the response gains a `timelineItems` array: items with `type === 1` are the blog's own posts/reblogs (use `.post`), and items with `type === 2` are like/comment activity clusters to be filtered out. The server keeps echoing a non-null `nextPageToken` after the last page, so a feed must also stop when a page returns fewer than `page_size` type-1 items.
- Some blogs return the **same media entries across many posts** from `list-blog-activity`. For example, `https://bdsmlr.com/blog/Rectrix` shows three identical images in nearly every post. This looks like a server-side media bug, not author content. The profile "Hide repeating images" option compares the three most recent image posts, takes the most common image identities that appear in at least two of them, and strips them from feed cards and RSS. URLs are matched by path with signed query strings, media-proxy prefixes, and file extensions removed (`src/lib/repeatingImages.ts`). RSS uses `hide_repeating_images=1`.
- Sorting by **Most popular** (`sort_field: 6`) can return the same page again on the next page request. Feeds should dedupe by post id and treat a page with no new ids as the end of pagination (`src/lib/feedPagination.ts`).
- Profile search does **not** use `list-blog-activity`; it uses the same `searchPostsByTag` call as the global search with the query prefixed by `blog:<blogName> ` (e.g. `blog:aphroditeenthroned chastity`), so it shares that endpoint's session/`hasMore` pagination and `resultUnits` response. The unfiltered profile feed still uses `list-blog-activity` as described above. Do not send a query (`q`) to `list-blog-activity`.
- `searchPostsByTag` request field is **snake_case** `tag_name` (same query syntax as `listBlogActivity`'s `q`). Pagination is **session-based, not cursor-based**: the first request sends `page: 1` (integer) with no `session`, the response returns a `sessionId`, and every subsequent request sends `page: 2, 3, …` (incrementing integer) plus `session: <previous response's sessionId>`. There are no working page tokens for this endpoint (`page.nextPageToken` is returned but ignored; only the integer `page` advances). The response is a list of **result units** (`resultUnits[]`), where each unit is `{ post }` or `{ reblogGroup: { count, label, originPostId, representativePostId, posts[] } }`; `posts[]` is a legacy mirror that holds `null` in slots occupied by a reblog group. With `variants: [1]` (original-only) every unit is a plain post. Use `hasMore` as the authoritative "there is a next page" flag: `sessionId` is now always returned, even when the search is exhausted, so `!sessionId` must **not** be used to stop. `searchStatus` is `"warming"` on a cold search and can return zero units on the first page before settling, so retry a few times while it is `warming` with no units and `hasMore` true; it is `"exhausted"` at the end.
- `getBlog` for a **private** blog when unauthenticated returns **HTTP 404** with `{"error":"blog not found"}` (not a 200 with an empty blog). The `rssApi` client surfaces this as a thrown `Error`, and callers must treat a failed/anonymous `getBlog` for a resolvable `blogId` as "private".
- `getBlog` returns `avatarUrl` and `coverUrl` wrapped in a broken media proxy prefix: `https://media.bdsmlr.com/gallery-grid/s3://ocdn012.bdsmlr.com/...`, which 404s. Strip `https://media.bdsmlr.com/gallery-grid/s3://` and use `https://ocdn012.bdsmlr.com/...` (query string preserved) to get a working signed URL. `unwrapMediaUrl` in `src/lib/sanitize.ts` does this; `getBlog` in both `api.ts` and `rssApi.ts` normalizes the fields before returning them.
- Internal write endpoints (`/v2/api/internal-write/like`, `/unlike`, `/reblog`, `/comment`) take **camelCase** `postId` and `actingBlogId`. As of October 2026 they reject the `v2_session` cookie and the API login token with **HTTP 401** `{"error":{"code":"unauthorized","message":"session required"}}`, and `batch-get-like-states`/`batch-get-reblog-states` fail the same way. The bundled OpenAPI now shows a required `actor` object (`v2SignedActorAssertion: { token }`) instead of `actingBlogId`, but the API login response does not return such a token. The working write path is the legacy web session (see next bullet).
- Legacy reblog uses the same web session as messages (`bdsmlr7_session` + `X-CSRF-TOKEN`). First `POST https://bdsmlr.com/reblog/<postId>` with `thispost=<postId>&orgpost=<originPostId|postId>`; the HTML response contains the composer (`#selectblog`, `.type[data-type]`, `.infopost[data-id][data-rb]`, `.blogreblog[data-blogid]`). Then `POST https://bdsmlr.com/reblogpost/<postId>` with urlencoded `thispost` (note HTML), `blog` (active blog id), `earlier=1`, `earliercomments` (may be empty), `type`, `blogid`, `originalid`, `rbid`, `typerb` (`0` live, `1` queue, `2` draft), and repeated `tags[]`. The submit returns an empty 200 even when it does not create a duplicate, so do not use the response body as a success signal. The app proxies both steps through `/api/legacy/*` (`src/lib/reblog.ts`).

- Legacy authoring uses the same web session. Live/queue/draft endpoints are `savetext`/`savetextqueue`/`savetextdraft`, `savequote`/`savequotequeue`/`savequotedraft`, `savechat`/`savechatqueue`/`savechatdraft`, `savelink`/`savelinkqueue`/`savelinkdraft`, `newimgpost`/`newimgpostqueue`/`newimgpostdraft`, `savevideopost`/`savevideopostqueue`/`savevideopostdraft`, and `saveaudio`/`saveaudioqueue`/`saveaudiodraft`. Text, quote, and chat take `thispost`, `blog`, repeated `tags[]`, and `title`. Links take `blog`, `description`, `image`, repeated `tags[]`, `title`, `url`. Photo takes `comment`, `blog`, repeated `tags[]`, and `captcha`. Video and audio take `comment`, `blog`, and repeated `tags[]`. Media uploads go to `/savephotos`, `/savevideo`, and `/savemusic` with multipart `_token`, `blog`, and `file`. Photo uploads and the photo `captcha` use the hidden composer `#token` returned by `POST /addphoto`, while video and audio uploads use the page meta CSRF token. Composer fragments are POST-only (`/addtext`, `/addphotoq`, etc.); `getLegacyComposerToken` returns both tokens. All writes need the `X-CSRF-TOKEN` meta token from `/dashboard`; Cloudflare can challenge or rate-limit these legacy writes.
- Draft and queue editors share the same shape. `POST /editdraft` or `POST /editqueue` with `id` returns the editor HTML (`#titleedit`, `textarea#editthis`, `.type[data-type]`, `.thisedit[data-postid][data-comment]`, `#Tags li`, `.blogID[data-blog]`). Save drafts with `POST /editdraftpost/` and queue posts with `POST /editqueuepost/`, both using `thispost`, `blog`, repeated `tags[]`, `type`, `title`, `textpost`, `postid`, `nocomment`, `textpostcase`, `blogid`, and `earlier`. Published posts save with `POST /editpost/<postId>` using the same fields. Draft actions are `/publishpostdraft`, `/publishpostdrafttoqueue`, and `/draftdelete` with `id`. Queue actions are `/publishpost`, `/queuedelete`, `/queueCalendar` (`year`, `month`, `day`, `hour`, `postId`), `/qchanges`, `/queuepause`, `/qtimefirst`, `/qtimesecond`, `/qtimequeue`, `/randomqueue`, and `/timezonechange`.
- The queue page is `/queuev2`. Items are `.newsfeed .news.panel[id]` with `.post_content`, `.titletext`, `.textcontent`, `.tags`, and a `.fa-calendar[data-time][data-postid]`. Drafts are `.wrapqueuepost[id]`. `/massedit` lists published posts and supports `/tagsmassedit`, `/masscaptionsedit`, and `/postdeletemass`, but not full body editing.
- A legacy reblog returns an empty 200 even when it creates nothing, and `list-blog-activity` can lag by minutes before it includes a new reblog. `/massedit` shows the new post immediately as `.postitem[data-id]`. The app records the latest massedit post ids before a live reblog, checks them again after submit, and only then marks the reblog as done. It also stores a 30-minute pending-reblog card in localStorage so the post appears at the top of the user's profile until the activity feed catches up. Queue reblogs skip this check.
- As of October 2026, BDSMLR returns HTTP 500 for `/draftdelete` and `/publishpostdraft` even from the official web UI. Surface a clear error and do not treat an empty success as guaranteed. The app still implements the documented actions for when the server recovers.
- Comments: `list-post-comments` takes **camelCase** `postId` and a `page: { pageSize, pageToken? }` object; the response has `comments[]` (`id`, `postId`, `userId`, `blogId`, `blogName`, `body`, `createdAtUnix`) and `page.nextPageToken`. The comment `body` is HTML, usually `<pre data-format="md">…</pre>`, so render it as text or sanitize it before display. Posting uses `/v2/api/internal-write/comment` with **camelCase** `{ postId, comment, actingBlogId }`, the same `v2_session` cookie as likes/reblogs, and returns `{ ok, action, postId, actingBlogId }`.
- Messaging does **not** live on `api-prod`: it is a Laravel app on `bdsmlr.com` with its own session. `GET /messages/bootstrap` returns `{ threads, history }`, `GET /messages/threads/<id>` returns `{ thread, messages, next_before }`, and `POST /messages/messages` takes `{ to: <blogName>, body }`. Both the inbox and send require the `bdsmlr7_session` cookie, and writes also need `X-CSRF-TOKEN` copied from `<meta name="csrf-token">` on `/messages` (the `XSRF-TOKEN` cookie form does not work). Our app performs a separate web login at `/login` (`_token`, `email`, `password`, `remember`) to obtain those cookies, strips `Domain` from every `Set-Cookie`, proxies `/api/messages/*`, and re-fetches the CSRF token before each write. If the web session is missing, `/api/messages/*` returns 401. A text send returns `{ thread_id, target: { name, avatar_url }, message }`; `/messages/messages/image` accepts the same `to` plus a multipart `image` field and returns the same shape. The proxy must preserve the multipart content type and send the raw body. Thread actions are `POST /messages/threads/<id>/block` (toggles and returns `{ blocked }`), `/clear` (removes the conversation for the current user), and `/delete` (archives it, despite the name). `GET /messages/recipient?to=<blogName>` resolves a recipient.
- Hidden write endpoints used by the BDSMLR web client but absent from the bundled OpenAPI: `POST /v2/internal-write/follow`, `/unfollow`, `/block`, `/unblock`, `/report-blog`, `/report-post`, and `/delete`. They take camelCase `actingBlogId` plus either `targetBlogId` (follow/block/report-blog) or `postId` (report-post/delete); report-blog also takes `reason`. Follow state is `POST /v2/blog-follow-state` with `{ actingBlogId, targetBlogId }` and returns `isFollowed`. Followers use `blog-follow-graph` with `direction: "followers"`, siblings use `POST /v2/list-blog-family-blogs` with `{ blog_id }`, and the block list is `POST /v2/get-blocked` with `{ user_id }`.
- Discovery endpoints: `POST /v2/for-you` takes `{ perspective_blog_name, page_size, page_token? }` and returns `{ posts, page.nextPageToken }`. `POST /v2/related-posts` takes `{ seed_post_id, perspective_role, perspective_blog_name?, page_size?, page_token? }` and returns the same post list shape. `POST /v2/list-recommended-blogs` takes `{ blog_name, limit }` and returns `{ blogs }`, but it currently returns an empty list for many blogs.
- `POST /v2/search-blogs` takes `{ query, page: { page_size, page_token? } }` and returns `{ blogs, page.nextPageToken }`. `search-tags` and `list-user-activity` currently return HTTP 500, so build activity from `list-blog-activity` instead of `list-user-activity`.
- `list-post-likes` and `list-post-reblogs` take **snake_case** `post_id` plus `page: { page_size, page_token? }`, and return `{ likes | reblogs, page.nextPageToken }`. Activity `timelineItems` clusters (`type: 2`) carry `cluster.label` (`"Likes"`, `"Comments"`) and `cluster.interactions` posts.
- `list-blog-top-tags` counts are approximate and can be much larger than the number of posts a blog tag search returns for the same tag (for example, Top tags reports 9,117 for a tag while the blog search returns 2). The profile UI shows a clarification when a single-tag search completes with fewer posts than the Top tags count. Treat these counts as a hint, not an exact blog-scoped total.
- `POST /v2/blog-tag-affinity` takes `{ blog_name }` and returns `{ blogId, blogName, tagAffinity }`, where `tagAffinity.all.both`, `.likes`, and `.reblogs` are arrays of `{ tag, count }`. `get-blocked` returns `{ blockedBlogIds, blockedUserIds }`, and it can include the current user's own blog and user, so filter those out before display.
- Legacy account and blog settings use `POST /changemail` (`passwd`), `POST /changepassword` (`passwd`, `passwd2`), and `POST /changeusername/<name>` (`username`). Blog customization saves through `POST /customizesave/<blogId>` with the full field set from `GET /customize/<blogName>`, including `title`, `description`, `Style`, `font`, color fields, `avatar_shape`, toggles, and interests. Avatar uploads go to `POST /customizedz/avatar`; header images use `POST /customizesave/backgroundhd/<blogId>` and blog backgrounds use `/customizesave/background/<blogId>`, both with `_token` and `file`. Drafts are listed at `GET /drafts`; actions are `POST /publishpostdraft`, `/publishpostdrafttoqueue`, and `/draftdelete` with `{ id }`. Some of these legacy actions currently return HTTP 500 on BDSMLR.
- `.gif` files may be served as `video/mp4`, but an alternate can also be a dead link while the original GIF still works. The UI keeps fallback media candidates and switches on media load errors.
- `.gif` files may be served as `video/mp4`. Media URLs are chosen by extension heuristic in `getPostMediaUrls` (`src/lib/sanitize.ts`): a mime-typed `original` wins; else a static-image `original` extension (jpg/png/webp/…) wins; else a mime-typed `alternate` wins; else `original.url` as last resort. A `.gif` original defers to a mime-typed `alternate` because the CDN may serve it as `video/mp4`, which an `<img>` cannot decode. Keep `src/lib/sanitize.test.ts` in sync with any change here, and reference the real posts in `docs/media-cases.md`.
